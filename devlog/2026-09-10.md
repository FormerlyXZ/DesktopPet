### 背景

用户提出要为桌宠增加「养高木同学」玩法：鼠标悬停弹出喂食等选项、食物获取途径、喂食后的表现动画、
以及类似聊天气泡的台词系统（待机说话、喂食后说话、检测用户在做什么并相应说话）。
美术要求与《擅长捉弄的高木同学》风格相配，且**不得复用现有右键设置/设置面板的冷蓝磨砂美术**。

本日任务定位为「前续准备」：摸清现状 → 调研通用做法 → 与用户确认关键决策 → 产出配套文档。

### 现状调研（结论）

- 现有 Q版交互已占用：悬停(害羞) / 长悬停3s(问号) / 单击(惊吓+弹功能面板) / 双击(生气→哭) / 键盘 / 音频 / 静音 / AFK / 夜间睡眠待机
- `PetWindow` 已具备：透明+置顶+mask、拖拽阈值 5px、400ms 双击检测
- `BubblePanel`（左键功能面板 / 右键系统面板）与 `panel_animator` 可直接复用
- `InputMonitor`（按键/活动）、`AudioMonitor`（播放/静音）、`GifCharacter._schedule_timer`（每分钟）可直接复用
- `GifRegistry` 已能按正则自动发现新 GIF → 动画映射下拉框可自动跟上

### 素材清点（36 个 GIF 全部实测）

用 `QImageReader` 批量扫描 + 抽帧拼接触印相表人工查看，结论：

- 全部 **500×500、带 alpha、17~88 帧、0.66~3.0 MB**
- **没有专门的「吃」动画** → 喂食必须走「食物→GIF 映射表 + 四级兜底链」
- 有道具、可当"收到东西"反应的：`蛋糕`（捧插蜡烛蛋糕）、`红包 1`（红包+金币）、`玫瑰`（中段才举起玫瑰）、
  `复活节`（提彩蛋篮）、`庆祝`（彩带礼花）、`荧光棒 2`、`通知_提示 爱心_喜欢`（爱心浮起+脸红）
- 可用于拒绝/尴尬：`汗`、`生气`；用于开心：`笑`、`点赞`
- **已知缺陷**：`冒泡 2` 与 `睡觉(普通)` 含**不透明黑色边缘块**，叠加桌面会显出一块黑矩形 → 默认不进养成动画池

### 发现并已写入文档的三个硬问题

1. **命名冲突**：项目里「气泡」已被 `BubblePanel`（菜单）占用。新功能头顶说话框统一定名为
   **「对话气泡 / SpeechBubble」**，文档中不简称"气泡"。
2. **悬停菜单点不到**：菜单是独立窗口，鼠标从人物移到菜单会触发 `leaveEvent` → 现有逻辑立刻把角色
   从「害羞」打回「加油」，菜单也会因 `focusOutEvent` 收起。需要 **350ms 宽限期 + `menu_entered` 取消宽限**
   双向机制（详见技术方案 4.8a）。
3. **对话气泡绝不能抢焦点**：必须 `WindowDoesNotAcceptFocus` + `WindowTransparentForInput` +
   `WA_ShowWithoutActivating`，且**不得照抄** `BubblePanel.popup_at()` 里的 `activateWindow()`，
   否则用户打字时输入焦点会被抢走。

### 问题记录（单测抓出的 3 个真实缺陷）

1. **`date.fromisoformat()` 跨版本行为不一致**
   Python 3.11+ 会接受紧凑日期 `20260910`，3.10 不接受。存档是用户可手改的 JSON，
   行为随解释器版本漂移不可接受 → 加严格正则 `^\d{4}-\d{2}-\d{2}$` 预校验。
   （本机是 Python 3.14，正是因为 3.14 接受了紧凑形式才暴露出来。）

2. **等级表缺 `threshold` 键的条目会被当成阈值 0**
   原实现用 `safe_int(item.get("threshold"))`，缺失即 0。`levels.json` 里一条手误的条目
   就会把整张 6 级表压成单级，且**不报错**。改为：没有合法 `threshold` 的条目直接丢弃，
   过滤后为空才回退代码内兜底表。这样既不会因一条坏数据废掉整张表，也不会静默降级。

3. **存档里空名字的库存条目会变成面板上的空白卡**
   `{"": 5}` 这种条目原样通过读档。改为在读档时丢掉空名条目（与 `add_item` 已有的
   空名校验保持一致）。

另有两个设计取舍在实现中定稿（已回填 `02-技术方案.md` 4.1）：

- `checkin_reward()` 返回**档位→数量**而非物品名 → 规则层不该知道"奶油面包"这种素材名称，
  否则用户在 `items.json` 里改个名就会打断规则层单测。物品名映射交给 `resolve_tiers()`。
- 签到奖励表新增 `assets/nurture/checkin.json` → 遵循"数值可外部配置"原则。

**已知无害约束**：`NurtureStore` 内部持有 `QTimer`，必须在 `QApplication` 创建之后实例化，
否则控制台会出现 `QObject::startTimer: event dispatcher has already been destroyed` 警告
（只是噪音，不影响功能）。阶段 D 在 `main.py` 里连线时天然满足。已写入文档。

1. **`DialogueLibrary` 做成普通类，不继承 `QObject`**（原方案写的是 `QObject`）。

### 问题记录

**1. `hide_with_anim()` 是异步的 → 固定 sleep 让测试 20% 概率随机失败**

`hide_with_anim()` 跑的是 160/180ms 的 `QPropertyAnimation`，动画结束才真正 `hide()`。
第一版测试用 `QTest.qWait(260)` 等它，结果**跑 5 次失败 1 次**。
修法不是把 sleep 加长（那只是降低失败率），而是**轮询等条件成立**：

```python
def wait_until(self, predicate, timeout_ms=2500, step_ms=25) -> bool:
    ...
```

改完之后连跑 8 次全绿。**这条经验已写进 `CLAUDE.md`** —— 项目里所有面板动画都是异步的，
以后写 UI 测试还会踩到。

**2. `under_mouse()` 读真实全局光标 → 测试结果取决于"跑测试的人鼠标在哪"**

`_on_hover_grace_timeout()` 里有一句"光标确实还在菜单上就不收"的兜底，读的是 `QCursor.pos()`。
在实机验证脚本里，光标恰好落在菜单矩形内时，"宽限期到期该收菜单"的断言就失败了 ——
鼠标挪一下结果就变。

修法：测试里把它替换成可控桩（默认 False），**两个分支各写一个用例**
（`test_grace_timeout_without_ever_entering_the_menu` /
`test_grace_timeout_keeps_the_menu_if_the_cursor_is_on_it`）。

**3. 真实缺陷：鼠标回到人物后，被推迟的 leave 标记没清 → 可能补发两次 leave**

这是**单测抓出来的产品 bug，不是测试写错**。
原实现只在宽限期到期时清 `_hover_leave_deferred`，于是：

```
离开人物（菜单开着）  → deferred = True
回到人物              → deferred 仍是 True          ← 问题在这
之后真正离开（菜单已被点击关闭 → 走 else 分支直接调了 handle_mouse_leave）
之后某次宽限期到期    → 又补发一次 handle_mouse_leave()   ← 发了两次
```

修法：`enterEvent` 里把 `_hover_leave_deferred` 清掉 —— 鼠标回到人物 = 悬停恢复，
那次 leave 不再欠着；之后再离开时自然会重新判断。
新增 `test_no_double_leave_after_hover_resumes` 锁住这个行为。

**4. 启动序列期间菜单会弹（已知缺口，留阶段 D）**

`is_busy()` 是阶段 D 才加到 `CharacterController` 的方法。阶段 C 用 getattr 能力探测，
`is_busy` 不存在就返回 `False`，所以启动动画（到达→加载→加油）期间悬停仍会弹菜单。
**这是刻意的折中**：不为了这一个判断把阶段 D 的接口提前搬过来。阶段 D 落地后自动修好。

> 顺带一提：实机验证脚本第一次跑时正是被这个绊了一下 —— 启动没播完时
> `handle_mouse_enter()` 被 `state == STARTUP` 吃掉，导致 5 条断言假阴性。
> 那是角色自身的既有设计，不是本次改动引入的；脚本里加了"等启动序列播完"的前置步骤。

### 设计取舍（已回填 `02-技术方案.md`）

1. **动效不复用 `panel_animator`**：它把位移量硬编码成 40px，对一条 44px 高的胶囊太大，
   会像"飞进来"。规范第 6 节要求悬停菜单位移 12px、弹出 200ms、收起 160ms，所以自己实现。
2. **`plan_placement()` 与 `popup_near()` 拆开**：动画一跑位置就在变，位置断言会变得不可靠；
   而"菜单会不会跑到屏幕外"恰恰是这组件最值得自动化验证的地方。拆开后落位变成纯几何可断言。
3. **左右间距做成对称**：初版右侧隔 7 像素列、左侧隔 8 列（差 1px，`QRect` 右边缘闭区间的经典坑）。
   统一成两侧都恰好隔 8 列。
4. **菜单不加窗口 mask**：胶囊四角与顶部提示条留白区会吃掉鼠标事件，但菜单是临时弹层（几秒），
   加 mask 反而会让抗锯齿描边变毛边。对话气泡（阶段 E）才必须做鼠标穿透。

### 设计取舍（已回填 `02-技术方案.md` 4.9 / 4.11）

| 取舍 | 决定 | 理由 |
|------|------|------|
| 连点防护的起点 | **送出瞬间** +300ms（01 文档写的是"动画结束 +300ms"） | "动画结束"目前没有信号可听（`interaction_finished` 声明了但从未 emit）；300ms 时长与目的不变，只是起点提前，而动画期间面板本来就收起了 |
| 素材全缺时 | **照扣库存、照出台词** | 送出的是那份点心，不是那段动画；把库存退回去反而让人困惑 |

| 面板不收自己 | 关闭按钮只发 `close_clicked` | "关闭"与"送出去后自动收"走同一条路，收不收由 controller 决定 |

   顺带在测试里补了两条方向断言（正常与翻转各一条）。
3. **`QRect.bottom()` 是闭区间**，尾巴尖的公式少了个 +1（单测抓到的：469 vs 470）。
   同理居中要用 `(width - 1) // 2` —— 这已经是本项目第三次踩同一个坑（菜单、面板、气泡）。
4. **`NurtureStore._normalize()` 只认 `FLAG_DEFAULTS` 里的 flag**。我原本打算用
   `f"{scene}_date"` 动态记"今天问候过了"，那样的键**活不过一次重启** ——
   表现是"每次启动都重新问候一遍"。改成在 `FLAG_DEFAULTS` 里显式列出四个时段标记。
5. **01 文档 7.2 与 7.3 打架**：`detect_typing` 的触发条件是"打字速率 > 阈值"，
   而 7.3 第 2 条说"高频打字 → 主动台词暂停"。两条都照做的话这条台词**永远不会出现**。
   裁定：就事论事的观察类台词（`detect_typing` / `detect_typing_long`）不受专注保护，
   其余主动台词照旧静默。代价是要多一个 `FOCUS_EXEMPT_SCENES` 集合 —— 值得，因为另一条路是死代码。
6. **配置键名对不上**：我按 01 文档写的是 `mute_start` / `mute_end`，
   而 `config.py` 里实际叫 `mute_hours_start` / `mute_hours_end`。用户真在设置里改了时段的话，
   这个 bug 的表现是"静音时段永远按默认 23-7 算"，很难发现。已修，并把那条测试改成**把时间钉死**
   （否则它的成败取决于跑测试的时间）。
7. **`bubble_anchor_ratio` 与角色自报比例打架**：两者都想要"头顶在哪 14%"这个数。
   定稿：配置里那个 0.14 表示"未自定义"，此时用 `character.speech_anchor_ratio()`
   （PNG 与 GIF 的头顶留白不同）；用户改成别的值才覆盖。

### 设计取舍

| 取舍 | 决定 | 理由 |
|------|------|------|
| 动效 | **自实现 8px**，不用 `panel_animator` | 后者位移硬编码 40px，对小气泡像"从屏幕外飞进来"（与菜单/面板同一取舍） |
| 断行 | 自己按像素宽度逐字断 | `drawText` 不支持 1.55 倍行距，且"最多 4 行 + 省略号"本来就要自己数行 |

## 下半场（续）：阶段 F —— 获取途径（签到 / 陪伴兑换 / 打字兑换 / 彩蛋）

> 目标：**让食物自己长出来**。阶段 D/E 之前库存只能靠手塞存档，这一阶段把 01 文档第 4 节

### 实现要点

| 途径 | 规则 | 落点 |
|------|------|------|
| 签到 | 每天一次；连签 3/7/14/30 天给里程碑；**时间回退不发放不重置** | `controller.try_checkin()`（菜单 + 托盘两个入口） |
| 陪伴兑换 | 累计活动 60 分钟 → 普通食物 ×1，上限 3/天 | `accrue_activity()` + 每分钟心跳结算 |
| 打字兑换 | 累计 2000 键 → 普通食物 ×1，上限 2/天 | `report_key_press()` 计数 + 心跳结算 |
| 彩蛋 | 整点 25%（日上限 3）/ 长待机 10 分钟（每天 1 次）/ 节日表 / 首次使用 | `_check_hourly_egg` / `_check_afk_egg` / `_check_event_egg` / `_check_first_run_egg` |

三条贯穿全阶段的约定（写进了 02 文档 4.11，改这一节前必读）：

1. **发放与播报解耦** —— 物品先到手，台词说不说得出来是另一回事
2. **记日期的 flag 只在真的说出来了之后才写** —— 阶段 E 的教训，否则被挡一次就整天不再说
3. **播动画是尽力而为** —— 签到不因"她正忙"而拒绝；奖励是用户的，动画只是表现

### 结构决策

| 取舍 | 决定 | 理由 |
|------|------|------|
| 按键/活动计数放哪 | **放 controller**，`input_monitor.py` 保持零改动 | 只有养成层要用这个数（阶段 E 已按同一理由做过一次打字速率）。代价：计数与用法耦合在一个文件里，阶段 G 若别的功能也要，再搬回 monitor |
| 活动时长怎么算 | 相邻两次 `any_activity` 的时间差，**单次截断 5 秒** | 信号本身不带时长；不截断的话"挂机 3 小时后的第一次鼠标移动"会一口气折算出 180 分钟，直接换出 3 份食物 |
| 进度什么时候落盘 | 内存累加，**每分钟心跳回写**（值没变就不写） | 鼠标移动每秒几十上百个事件，每次都 `store.save()`（发信号 + 重启防抖计时器）纯属浪费。代价：强杀进程最多丢一分钟进度 |
| 签到被拒绝时怎么反馈 | 两个新结果码 `already` / `clock_back` + 各一条台词 | 与 `try_send()` 的九个码同风格，方便测试与排查 |
| 一次点击说几句 | **只出一句**：库存满 > 里程碑 > 普通签到 | 气泡是替换不是叠放，挨个说只会剩最后一句（原本实现确实说三句） |
| 整点彩蛋的触发时刻 | "每个小时掷一次"而不是"`:00` 时掷" | 心跳 60 秒一次、起跳时刻由进程启动时间决定，卡"分钟数 < 5"会大概率整小时掷不到 |
| 整点彩蛋的日上限 | 补了个 `hourly_bonus_daily_cap = 3` | 01 文档只写了 25% 概率；不加上限时挂机一整天能白拿十几次 |
| 活动的三个 flag | `last_event_date` 等**显式写进 `FLAG_DEFAULTS`** | 这个坑阶段 E 踩过一次（`time_*_date`）：按场景动态拼键名的 flag 读档时会被丢掉 |

### 问题记录（都在写测试/跑真机时抓出来的）

1. **`convert_to_items()` 会把同一份进度反复兑换** —— 阶段 A 的实现里 `already` 只用在
   "还剩几个额度"上：`granted = min(progress // per, cap - already)`。心跳每分钟跑一次，
   于是"进度 2 份、已兑 1 个、上限 3"时**每次心跳都能再兑 1 个**。
   真机表现是"挂着不动，食物自己一直涨"。已改成 `min(progress // per - already, cap - already)`，

3. **测试里"事前设 flag"被 `store.load()` 冲掉** —— `NurtureController.__init__` 会调

   表现是"每个 tick 测试都被首用彩蛋抢走那句话"。所有阶段 F 的 tick 测试都要在**构造之后**设 flag。
4. **测试 fixture 的台词文件名少了 `.json`** —— `DialogueLibrary` 只扫 `*.json`，
   于是 15 个场景一个都没加载，测试静默地退回到内置兜底台词（`idle_random` 说的是内置那句）。
   教训：**fixture 的文件名要和真实目录一致**，否则"加载失败"会伪装成"逻辑正确"。
5. **库存满时 `_grant_bonus()` 什么都不说** —— 原实现只在"真的发出去了"时才说那句场景台词，
   于是库存满时只出「拿不下啦」，用户看不到"你签到了"这件事。改成库存满也照说。
6. **`test_real` 里程碑断言的坑**：台词里的 `{streak}` 占位符是**格式化后**才说出来的，
   拿原始模板去比会失败（验证脚本自己写错过一次）。

## 下半场（续）：阶段 G —— 前台窗口感知（隐私红线所在）

> 目标：让她知道**你在用什么类型的软件**，从而决定"该不该开口"。
> 这一阶段的成败标准不是功能多不多，而是**隐私自查过不过**：默认关闭 + 只出分类。

### 实现要点

| 部分 | 内容 |
|------|------|
| `src/window_monitor.py`（新，约 470 行） | ctypes 探针（`GetForegroundWindow` → `GetWindowThreadProcessId` → `OpenProcess(QUERY_LIMITED_INFORMATION)` → `QueryFullProcessImageNameW`）+ 全屏几何判定 + `QTimer(1000ms)` 边沿触发 + `create_monitor()` 唯一创建入口 |
| `assets/nurture/apps.json`（新） | 219 条进程名 → 5 个分类；26 条「不要感知」黑名单（密码管理器 / 远程桌面 / Windows 安全界面）；带 `_说明` |
| `nurture_model.py` | +`APP_KEYS` / `UNKNOWN_APP_KEY`（分类词表只此一份，`window_monitor` 与 `apps.json` 共用） |
| `nurture_controller.py` | +`on_fullscreen_changed` / `attach_window_monitor` / `foreground_detection_enabled` / `foreground_detection_active` / `current_app_key` / `is_fullscreen` / `_proactive_allowed`；`_focus_mode` 改用 `model.is_focus_mode`（真数据源齐了）；`_tease_allowed` 接上真实打字速率与连续时长 |
| `main.py` | +`_start_foreground_monitor()`（单独拎出来是为了可单测 —— `_start_monitors()` 会连带拉起 pynput 全局钩子） |
| 台词 | 新建 5 个 `detect_app_*.json`，各 8 条 |

### 结构决策

| 取舍 | 决定 | 理由 |
|------|------|------|
| 全屏算不算一种"应用分类" | **不算**：多一个 `fullscreen_changed(bool)` 信号 | 同一个游戏窗口化 ↔ 全屏来回切时分类根本没变。塞进 `app_key` 就得凭空造一个 `"fullscreen"` 假分类，而 `is_focus_mode(fullscreen=...)` 这个既有参数正好等着一份真数据 |
| 全屏怎么判 | 纯几何：`DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)` + `MonitorFromWindow` + `GetMonitorInfoW`，与**那块**显示器比 | 用显示器矩形而非工作区：最大化窗口只盖到工作区（差一条任务栏），所以不会被误判。副屏负坐标也对。**真机实测**：Qt 的 `showFullScreen()` 与独占全屏的游戏都被判为全屏，2560×1440 下逐像素相等 |
| 读不到进程名怎么办 | 连着 **3 拍**（3 秒）读不到才降级成 `unknown`，不足 3 拍保持上次分类 | 02 文档同时写了"视为 unknown"和"不清空上次分类"，字面矛盾。拆成"抖动"与"持续"两种情况就都满足了：安全桌面/进程刚退出的抖动不该让她换台；而管理员进程、反作弊保护的**窗口化**游戏是持续读不到的 —— 这时"她还以为你在用上一个应用"恰恰是最不该开口的时候 |
| 窗口标题 | **完全不读** | 按进程名分类用不到标题。源码里 `grep` 不到取标题的 API，比"读到了不记"更硬。唯一额外读的是窗口**类名**，用于排除 `Progman`/`WorkerW`/`Shell_TrayWnd` —— 否则点一下桌面就会被当成全屏（桌面本来就盖满屏幕） |
| 黑名单的语义 | 返回 `unknown`，与"不认识的应用"**完全无法区分** | 连"这是一款密码管理器"都不该泄露。默认放入密码管理器、远程桌面（`mstsc`/`anydesk`/`teamviewer`/`sunloginclient`/`todesk`）与 `logonui`/`lockapp`/`consent` |
| 开关的启停权归谁 | `create_monitor()` 只负责建与连线，**启停交给 `controller.attach_window_monitor()`** | 设置页里关掉开关要**立即**停（不能等重启），而且"要停就停干净"：`set_config()` 检测到开关翻 `False` 时连 `app_key`/全屏状态一起清空 |
| 无 controller 时建不建 | **不建**（返回 `None`） | 没人可连的感知器不该偷偷跑起来 |
| `detect_app_*` 受不受专注保护 | 五个场景**都进** `FOCUS_EXEMPT_SCENES` | 否则 7.2 与 7.3 打架：会议软件下"主动台词暂停"会把「在开会呀」永远压住 —— 而那正是它唯一的时机场合。但**全屏是一道更早、更硬的闸门**，连观察类也不发（气泡会盖在人家的画面上） |
| 台词里用不用 `{app}` | 不用 | 资产测试明确要求感知类台词**不落到具体内容**（「代码」「视频」都在黑名单里）。既然不能落到具体，就不必引入"分类 → 中文名"的映射表：少一个活动部件，也少一处隐私面 |
| 整点/奖励通知在全屏时 | 照说 | 全屏静默管的是"主动台词"，签到/兑换走 `_speak()`（用户挣来的交代）。吞掉会变成"我明明签到了她却不理我" |

### 问题记录

1. **`wintypes` 只在 `if _IS_WINDOWS:` 里 import** —— `_window_rect()` 等函数体里直接用了
   `wintypes.RECT`，非 Windows 下这些名字根本不存在（靠调用链上的 early return 兜住）。
   能跑，但属于"依赖调用顺序才不出错"的写法 —— 已在注释里点明。
2. **探针里的 `_process_name(0xFFFFFF0)`** —— 无效 pid 时 `OpenProcess` 直接失败返回 `""`，
   正是"读不到"路径的真实复现（管理员进程 / 反作弊保护的游戏走的就是这一支）。
3. **`str(exe or "")` 会把脏数据变成假进程名** —— `classify_exe([])` 得到 `"[]"` 而不是空串。
   已改成**只接受 `str`**，其余一律当"读不到"。
4. **测试里"检查能不能说"的顺序错了两次** —— `on_app_changed()` 成功说出一句后会记下
   **场景冷却**（会议/游戏 30 分钟），所以再问 `can_speak(同一场景)` 必然是 `False`。
   正确写法是"先问能不能说，再说，断言返回值"。（验证脚本与单测各踩一次。）
5. **验收脚本自己也会被 90 秒全局最小间隔绊倒** —— 观察类台词豁免的是**专注/免打扰**，
   不豁免全局间隔。脚本里必须先清 `_cooldowns` 与 `_last_proactive_ts` 才能只留一个变量。
6. **真机跑的时候前台正好是全屏游戏**（`bf6.exe`）—— 分类是 `unknown`（表里没有），
   但 `fullscreen=True`，所以**保护照样生效**。这恰好证明了设计：
   分类表宁可漏也不能猜，而全屏保护与进程名无关。顺手把 `bf6.exe` 加进了 `game`。

### 问题记录（全是"看着对了其实没对"的那种）

1. **`QScrollArea { background: transparent }` 管不到 viewport** —— 视口是它内部的子控件，
   不显式声明就用系统默认底色，在奶白纸片上糊出一条**浅灰蓝色带**（预览图一眼可见）。
   要写两行：`QScrollArea > QWidget > QWidget` 与 `QWidget#qt_scrollarea_viewport`。
2. **`QGroupBox::title` 的背景不能用不透明奶白** —— 纸片底是 `rgba(255,249,246,242)`（半透明，
   壁纸会透一点上来），标题用不透明的 `#FFF9F6` 去盖那条边框，就留下一块**比周围更亮的补丁**。
   改成同 alpha 后与纸片完全融合。
3. **图钉图标改了三版** —— "圆头 + 竖线"在 20px 下是**气球**；"帽 + 梯形身 + 针"是**铲子**；
   定稿"顶栏 + 上箭头"，与「最小化到托盘」的下箭头正好成对。
   又一次印证规范里那句"图标必须先渲染到 20px 看过再定稿"。
4. **我一度以为图标退化成了 emoji** —— 实际是**缩略预览图太小看错了**（18px 图标在整窗预览里
   只剩几十像素）。放大 4 倍裁切后确认是矢量图标。教训：**判断小尺寸细节要看原图裁切，别看缩略图**。
5. **行高 34 → 36** —— 30px 圆形图标塞在 34px 行里，hover 胶囊的描边与图标圆只差 2px，
   两条线会糊在一起；多给 6px 就分得开。
6. **三个 `tease` 测试在 23:01 集体变红** —— `_tease_allowed()` 读**当前小时**，深夜禁区默认
   23:00~07:00，而 fixture 里 `set_config()` 是**整体替换**配置，只写 `tease_frequency` 会把深夜区间
   落回默认值。这是**测试依赖时钟**的老毛病（不是换肤引入的），已修：fixture 默认把深夜禁区设成
   零长度（= 无深夜时段），涉及 tease 的用例显式带上。
   **教训：换肤顺手跑一次全量，反而抓出了一个潜伏 bug。**
7. **新写的面板测试自己踩了异步动画的坑** —— `popup_at()` 的滑入是 220ms 动画，直接读 `x()`
   拿到的是动画起点（差 40px）。项目里早有这条经验（`hide_with_anim`），这次又踩一次，
   于是把 `wait_until()` 也复制进了新测试文件。
8. **冷蓝色源码扫描把我自己的注释也抓了** —— 新文件 docstring 里写了"原本是 `#42A5F5`"，
   扫描是**文本级**的，直接报错。改写成"冷蓝磨砂玻璃那套"（不带 hex），保持"原始 grep 干净"这条约束。

## 追加：悬停菜单不再"吃掉"单击（用户实机反馈）

> 用户原话：**"鼠标放在上面时弹出喂养菜单后单击不会弹出集成功能面板，必须要等喂养菜单消失后才能点出来"**

### 这不是换肤改出来的

排查结论：`src/pet_window.py` 这次换肤**一行没动**，问题出在阶段 C 按 01 文档 5.4
**特意写的**那条裁定上 ——

```python
# 修订前（_on_single_click_timeout）
if self.any_popup_visible(("hover",)):
    self.hide_all_popups()          # 菜单开着时，单击 = 收起菜单
    self._flush_deferred_leave()
    return                          # ← 不播惊吓、不弹功能面板
```

| 排查项 | 结论 |
|--------|------|
| 是换肤引入的吗 | **不是**。`pet_window.py` / `_on_single_click_timeout` 本次零改动 |
| 是悬停菜单吞了鼠标事件吗 | **不是**。菜单 `WA_ShowWithoutActivating` 且不实现 `focusOutEvent`，不抢焦点 |
| 是菜单窗口盖住人物、把点击吃了吗 | **不是**。用真 `config.json`（300px 人物停在屏幕底部附近）跑 `plan_placement()`：菜单落在 `y=1291..1381`，人物底边 `1289`，**重叠面积 0** |
| 真正的原因 | 就是上面那个 `return`：单击被裁定成"只收菜单" |

**关键旁证**：同一个局面下右键是能弹出系统面板的（`_toggle_system_panel()` 走仲裁器、
顺带收起菜单）。左右键行为不一致本身就是 bug，只是被"设计如此"这句话掩盖了。

### 修订后的规则（只有一句）

**单击永远等于「惊吓 + 弹出功能面板」**，悬停菜单开着时也一样；
收起悬停菜单交给 `_toggle_function_panel()` → `hide_all_popups()` 顺带完成
（互斥矩阵「同一时刻只有一个弹层可见」仍然成立）。

```python
# 修订后
self.character.handle_single_click()
self._toggle_function_panel()
```

用户在三选一里选了"**收起菜单 + 弹功能面板 + 播惊吓**"，即与"菜单没开时"逐字一致。
代价：每次点她都会播一次惊吓 —— 但那本来就是 Q版单击的既有行为，一致比"安静"重要。

### 教训

**"实机验收通过"只覆盖了当时被问到的那几条。** 阶段 C 暂停点的验收清单里，
"菜单开着时单击人物 → 只收菜单"是**作为期待行为**列出来让用户打勾的 ——
用户当时看到菜单收起、觉得没毛病就打了勾，直到真的用起来才发现"再也点不出功能面板"。
**清单问的是"符不符合描述"，而不是"好不好用"**；涉及交互直觉的裁定，
问法应该是"这个操作你觉得顺手吗"。
