## 1. 设计目标与约束

| 目标 | 约束 |
|------|------|
| 不侵入现有代码 | 默认服装（PNG）路径**一行不改语义**；Q版现有交互除 01 文档 5.4 明确裁定的 3 条外全部保留 |
| 不新增第三方依赖 | 前台窗口感知用 `ctypes`（与 `audio_monitor.py` 同风格），**不引入 psutil** |
| 可单独关闭 | 养成 / 对话气泡 / 主动说话 / 前台感知 四个开关互不牵连 |
| 可外部配置 | 食物、台词、节日、应用分类、等级阈值全在 `assets/nurture/*.json` |
| 可单测 | 数值规则写成**不依赖 Qt 的纯函数**，与项目现有"mock 时钟单测"习惯一致 |
| 崩溃安全 | 任何外部资源（台词/配置/动画/API）失效都必须优雅降级，不得影响桌宠本体 |

### 2.2 关键决策：为什么要有 `NurtureController` 这一层

如果把"能不能喂""该说什么"散落在 `PetWindow`、`HoverMenu`、`NurturePanel` 里，冷却和每日上限会变成一地散落的 `if`，必然出现"面板显示可点但实际不给"这类不一致。

**收拢为单一裁决点**：所有"要不要给 / 播什么 / 说什么"都问 `NurtureController`，UI 层只负责显示它返回的结果。UI 里不出现任何数值判断。

### 4.1 `nurture_model.py`（纯函数，最先写、最好测）


**实现时对原设计的三处修正**（原因见下）：

| 原设计 | 实际实现 | 原因 |
|--------|----------|------|
| `checkin_reward()` 返回 `{'items': {名称: 数量}}` | 返回 `{'tiers': {档位: 数量}}`，另加 `resolve_tiers()` 做二次映射 | 规则层不该知道"奶油面包"这种**素材名称**。用户在 `items.json` 里改名/增删食物时，规则层与它的单测完全不受影响 |
| `unlocked_features(level_index)` | `unlocked_features(level_index, levels=None)` | 解锁标识写在 `levels.json` 里，必须能传入；默认 `None` → 用代码内兜底表，保证配置缺失时降级不崩 |
| 签到奖励表无归属文件 | 新增 `assets/nurture/checkin.json` | 遵循"可外部配置"原则：数值可调，用户不用改代码 |
| `convert_to_items()` 的 `already` 只用于"还剩几个额度" | `already` 参与减法：`本次 = 进度折合份数 − already` | **阶段 F 抓到的真 bug**：心跳每分钟跑一次，只把 `already` 用在额度上时，同一份进度每次心跳都能再兑一个。表现是"挂着不动，食物自己一直涨"。原单测的所有用例两种口径答案相同，所以阶段 A 没暴露 |

> **单测范围**：跨天/连签回退、签到奖励边界、好感度截断、兜底链四级降级、语气禁区（深夜/专注/额度）、
> 兑换上限与零头、等级边界与解锁并集、脏值降级。全部是纯函数，不需要起 Qt 事件循环。
> 实际落地 **133 例**（`tests/`，`python -m unittest discover -s tests -t .`），其中另含
> `assets/nurture/*.json` 的**跨文件引用一致性**检查（食物动画名是否真的存在于素材库、
> 节日产出物品名是否存在、台词字数与"不评判"黑名单句式）。


### 4.2 `nurture_store.py`

```python
class NurtureStore(QObject):
    changed = Signal(str)          # 变更字段名（统一为 "state"），UI 据此刷新

    def load(self, today: date | None = None) -> None   # 容错读 + 坏档改名 + 跨天重置
    def save(self, immediate: bool = False)             # 2s 防抖；immediate 用于退出/签到
    def flush(self) -> bool                             # 强制落盘，写失败返回 False 不抛
    def reset_daily_if_needed(self, today=None) -> bool
    def cleanup_bad_files(self, keep: int = 3)          # 只留最近 3 个坏档

    # 访问器一律走属性/方法，不暴露裸 dict，避免外部绕过规则改值
    affection / streak / last_checkin_date / inventory(副本) / today()
    item_count(name) / has_room(name, cap) / add_item(name, n, cap) / take_item(name, n)
    bump_today(key, n) / bump_daily(key, n) / set_daily(key, v)
    stats(key) / bump_stats(key, n)
    flag(key) / set_flag(key, v) / mute_tease_today() / set_mute_tease(bool)
    used_lines(scene) / remember_line(scene, text) / forget_lines(scene)
```

**两条使用约定**

1. **必须在 `QApplication` 创建之后实例化** —— 内部 `QTimer` 依赖事件分发器，
   提前创建只会得到 `QObject::startTimer: event dispatcher has already been destroyed` 警告（无害但脏）。
2. **只在主线程使用** —— 防抖信号与 `QTimer` 都依赖主线程事件循环。

**阶段 F 用到的每日计数器与标记**（阶段 A 就已备好，这里记下各自的归属）：

| 键 | 段 | 用途 |
|----|----|------|
| `daily.active_minutes` | daily | 今日累计活动**分钟**（陪伴兑换进度，由心跳回写） |
| `daily.key_count` | daily | 今日累计按键数（打字兑换进度） |
| `daily.minutes_rewarded` / `daily.keys_rewarded` | daily | 今日**已兑换个数**（防重复发放的关键） |
| `daily.hourly_bonus_count` | daily | 今日整点彩蛋触发次数（配合下面的日上限） |
| `flags.first_run_bonus_granted` | flags | 首次使用彩蛋是否已发 |
| `flags.afk_bonus_date` | flags | 长待机彩蛋最近发放日期（每天一次） |
| `flags.last_hourly_hour` / `last_hourly_date` | flags | 整点彩蛋最近掷过的小时（同小时不重复掷） |
| `flags.last_event_date` | flags | 节日彩蛋最近发放日期（每天一次） |
| `flags.checkin_reminded_date` | flags | 签到提醒最近日期（每天最多提醒一次） |
| `stats.total_checkins` | stats | 累计签到次数（**`set_checkin()` 自己会 +1**，调用方不要再加） |

> **`flags` 只认 `FLAG_DEFAULTS` 里的键**：`_normalize()` 会把表外的 flag 丢掉，
> 所以"按场景动态拼键名"（如 `event_valentine_date`）活不过一次重启 ——
> 表现是"节日奖励每天都能再领一次"。一行日期就够表达"今天发过了"。
> 这个坑在阶段 E（`time_*_date`）和阶段 F（`last_event_date`）各踩过一次。

**跨天重置会把「今天不要捉弄我」一并复位**（该开关存在存档 `flags.mute_tease_date`，
不是 `config.json`），因为这本质是带日期的**运行时状态**而非用户偏好设置。

**原子写**：

```python
def _write_atomic(path, data):
    tmp = path + ".tmp"
    with open(tmp, "w", encoding="utf-8") as f:
        json.dump(data, f, ensure_ascii=False, indent=2)
        f.flush(); os.fsync(f.fileno())
    os.replace(tmp, path)          # 同分区原子替换
```

**坏档处理**：`json.JSONDecodeError` → `os.replace(path, path + ".bad-{ts}")` → 用默认值启动 → 记日志。**绝不静默删除用户数据**。

### 4.3 `dialogue.py`

```python
class DialogueLibrary:            # 普通类，不是 QObject（它没有任何信号）
    def __init__(self, dialogues_dir: str | None = None, store=None,
                 rng: random.Random | None = None)
    def reload(self) -> None                     # 支持热重载（设置里改完文件不用重启）
    def pick_line(self, scene, ctx=None, *, affection=0, tease_allowed=True) -> dict | None
    def pick(self, scene, ctx=None, **kw) -> str | None          # 便捷版，只取文本
    # 辅助
    def scenes() / has_scene(scene) / scene_meta(scene) / cooldowns()
    def all_lines() -> list[tuple[str, dict]]    # 配置自检用
    # 模块级
    is_proactive(scene) / is_gap_exempt(scene) / format_line(text, ctx)
    placeholders_in(text)
```

**实现对原方案的三处修正**

| 原设计 | 实际实现 | 原因 |
|--------|----------|------|
| `class DialogueLibrary(QObject)` | 普通类 | 它没有任何信号。做成普通类后**本模块完全不依赖 PySide6**，单测可以直接实例化，不用起 `QApplication` |
| `pick(scene, ctx) -> str` | 主接口是 `pick_line()`，返回 `{"text","tone"}` | controller 必须知道选中台词的语气，才能决定要不要计 `tease_count_today`。`pick()` 保留为只取文本的便捷版 |
| 过滤参数叫 `level_index` | 参数是 **`affection`（好感度）** | `min_level` 在 JSON 里写的是**好感度阈值**（如 250，与 `levels.json` 同刻度），不是等级下标。用下标比会把所有带门槛的台词永远过滤掉 |

**「文件存在但池为空」≠「没有这个文件」**（这条极易写错）：

* 用户显式写了 `"lines": []` → 那次**就不说话**（03 规范 9「允许沉默」）。
  此时不能悄悄用代码内兜底台词顶上去，否则用户永远关不掉一句话。
* 文件不存在 / 解析失败 → 用代码内 `DEFAULT_SCENES` 兜底，保证功能降级而不是变哑巴。

`pick_line()` 的完整流程：

1. 取场景池（用户文件优先；无文件/坏文件 → 代码内兜底；**空池 → 沉默**）
2. 过滤：`min_level > affection` 的剔除
3. 过滤：`tone == "tease"` 且 `tease_allowed` 为假 → **整组剔除**
4. 过滤：最近 5 条已用（`store.used_lines[scene]`）→ 剔除；若全被剔除则清空记录重来一轮
5. 按 `weight` 加权随机
6. 占位符替换（`{streak}` / `{level}` / `{hour}` / `{app}` / `{min}` / `{count}` / `{name}` / `{days}`）
7. 记入 `used_lines`

**占位符白名单**：只有 `ctx` 里显式提供的键能替换，`str.format_map` 配 `defaultdict`，
缺失键原样保留且不报错。模板本身写坏（落单的 `{`）也返回原文，**不抛异常**。

**场景分类**（模块级常量，controller 据此决定要不要过「全局最小间隔」）：

* `PROACTIVE_SCENES` —— 主动台词，受最小间隔与专注/全屏保护约束
* `GAP_EXEMPT_SCENES` —— **免于**最小间隔：用户直接触发的场景（喂食/签到/摸头…）与启动问候。
  用户点了却不说话是最糟的体验，所以这类场景一律不受 90 秒间隔限制。
* `store` 参数是**鸭子类型**（只需 `used_lines` / `remember_line` / `forget_lines`），
  存档写失败时静默跳过 —— 桌宠不能因为存档问题变成哑巴。

**ctypes 实现骨架**

```python
import ctypes, os, sys
from ctypes import wintypes

if sys.platform == "win32":
    _user32   = ctypes.WinDLL("user32",   use_last_error=True)
    _kernel32 = ctypes.WinDLL("kernel32", use_last_error=True)

    _user32.GetForegroundWindow.restype = wintypes.HWND
    _user32.GetWindowThreadProcessId.argtypes = [wintypes.HWND, ctypes.POINTER(wintypes.DWORD)]
    _kernel32.OpenProcess.argtypes  = [wintypes.DWORD, wintypes.BOOL, wintypes.DWORD]
    _kernel32.OpenProcess.restype   = wintypes.HANDLE
    _kernel32.QueryFullProcessImageNameW.argtypes = [
        wintypes.HANDLE, wintypes.DWORD, wintypes.LPWSTR, ctypes.POINTER(wintypes.DWORD)]
    _kernel32.CloseHandle.argtypes  = [wintypes.HANDLE]

PROCESS_QUERY_LIMITED_INFORMATION = 0x1000

def _foreground_exe() -> str:
    """返回前台进程的可执行文件名（如 'Code.exe'）；失败返回 ''。"""
    hwnd = _user32.GetForegroundWindow()
    if not hwnd:
        return ""
    pid = wintypes.DWORD()
    _user32.GetWindowThreadProcessId(hwnd, ctypes.byref(pid))
    if not pid.value:
        return ""
    h = _kernel32.OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION, False, pid.value)
    if not h:
        return ""                      # 权限不足（如管理员进程）→ 静默降级
    try:
        buf = ctypes.create_unicode_buffer(1024)
        size = wintypes.DWORD(len(buf))
        if _kernel32.QueryFullProcessImageNameW(h, 0, buf, ctypes.byref(size)):
            return os.path.basename(buf.value)
        return ""
    finally:
        _kernel32.CloseHandle(h)
```

- **必须显式声明 `argtypes`/`restype`**：64 位下 `HWND`/`HANDLE` 是 8 字节指针，不声明会被截断成 32 位 `int` 而随机失败。
- 轮询 `QTimer(1000ms)`，与上次分类比较，**仅变化时**发 `app_changed`（边沿触发，与 `audio_monitor.py` 同构）。
- **只暴露分类，不暴露原始进程名/标题**——`app_changed` 的字符串是查表结果。原始 `exe` 名只在 `WindowMonitor` 内部用于查表，**不进日志、不落盘**。
- 自查：把自己也排除（桌宠自己的窗口获得焦点时不算切换）。
- 读不到（`""`）→ 视为 `unknown`，不清空上次分类，避免闪烁式误触发。
- 非 Windows / 权限失败 / `json` 缺失 → 整个模块静默禁用，功能降级为"无前台感知"，其余照常。

#### 4.7.1 实现后记（阶段 G，已按此落地）

| 设计稿 | 实际实现 | 为什么 |
|--------|----------|--------|
| 只有一个 `app_changed(str)` | 多一个 `fullscreen_changed(bool)` | 全屏不是"应用分类"（同一个游戏窗口化/全屏来回切时分类根本没变），塞进 `app_key` 就会凭空多出一个 `"fullscreen"` 假分类。拆成两个信号后，`nurture_model.is_focus_mode(fullscreen=...)` 这个既有参数也终于用上了 |
| 只判"是不是全屏" | 几何判定：`DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)`（拿不到退回 `GetWindowRect`）+ `MonitorFromWindow` + `GetMonitorInfoW`，与**那块**显示器的矩形比 | 用显示器矩形而不是工作区：最大化窗口只盖到工作区（差一条任务栏），因此不会被误判成全屏。副屏负坐标也对 |
| 「读标题、本地匹配」 | **完全不读标题**：源码里 `grep` 不到任何取标题的 API | 按进程名分类根本用不到标题。不存在那条代码路径比"读到了不记"更硬。额外读的只有窗口**类名**，用来排除 `Progman`/`WorkerW`/`Shell_TrayWnd`（桌面/任务栏本来就"盖满屏幕"，不排除的话点一下桌面就会被当成全屏） |
| 读不到 → 视为 `unknown`，且不清空上次分类 | **连着 3 拍读不到**才降级成 `unknown`；不足 3 拍保持上次分类 | 两句要求本身是矛盾的，拆成"抖动"和"持续"两种情况就都满足了：安全桌面/进程刚退出这类一次性读不到不该让她换台；而管理员进程、反作弊保护的窗口化游戏是**持续**读不到的 —— 这时"她还以为你在用上一个应用"恰恰是最不该开口的时候。同一手法见 `audio_monitor.py` 的防抖计数 |
| `apps.json`：进程名 → 分类 | `{"categories": {分类: [进程名…]}, "ignore": […], "_说明": […]}` | 按分类成组比扁平表好看得多（用户会自己改这个文件）；`_说明` 与 `items.json` 同口径。加载时**只认 `APP_KEYS` 里的分类名**（写错 `brower` 就整组跳过），同名进程先出现的赢 |
| 黑名单"不要感知" | 命中的进程一律返回 `unknown`，和"不认识的应用"**完全一样** | 连"这是一款密码管理器"都不该泄露出去。默认已放入密码管理器、远程桌面、Windows 安全界面（`logonui`/`lockapp`/`consent`） |
| `main.py` 里创建 | `create_monitor(controller)` 是**唯一创建入口**，`main._start_foreground_monitor()` 只转一手 | 阶段 H 的设置页也要建它，两条创建路径迟早走偏。开关状态问 `controller.foreground_detection_enabled()`（**活配置**），不拿启动时的 config 快照 |
| 开关关掉 → 停 | `controller.set_config()` 检测到开关翻到 `False` → `monitor.set_enabled(False)`，**并把手里的 `app_key`/全屏状态一起清空** | "要停就停干净"：留一份内存里的旧状态没有意义，而且会让后续判断基于过期信息 |
| 第一拍 | **只记状态不发信号** | 启动那一刻"你现在开着什么"不是一次切换，她不该一睁眼就开始点评（与 `audio_monitor.py` 的 `_first_poll` 同构） |

**台词侧的裁定（写在 `nurture_controller.py`，不在这里）**：五个 `detect_app_*` 被放进
`FOCUS_EXEMPT_SCENES`（"就事论事的观察类"），而**全屏是一道更早、更硬的闸门** ——
全屏时连观察类也不发（气泡会盖在人家的游戏/演示/视频画面上，01 文档 7.3 第 3 条）。
两条一起看：窗口化会议/游戏下她能说"你在开会呀"，全屏下她一句话都不说。

#### (a) 悬停延迟 + 宽限期

```python
def enterEvent(self, event):
    self._hovering = True
    self._hover_grace_timer.stop()          # 回到人物 → 取消宽限
    self._hover_leave_deferred = False      # 悬停恢复 → 那次被推迟的 leave 不再欠着
    self.character.handle_mouse_enter()      # 原有
    if self._hover_menu_allowed() and not self._hover_menu.isVisible():
        self._hover_menu_timer.start(self._hover_delay_ms())
    super().enterEvent(event)

def leaveEvent(self, event):
    self._hovering = False
    self._hover_menu_timer.stop()
    if self._hover_menu.isVisible():
        self._hover_leave_deferred = True
        self._hover_grace_timer.start(self._hover_grace_ms())
    else:
        self.character.handle_mouse_leave()   # 原有行为
    super().leaveEvent(event)

def _on_hover_grace_timeout(self):
    if self._hovering:
        self._flush_deferred_leave()          # 又回到人物身上 → 不需要 leave
        return
    if self._hover_menu.under_mouse():
        return                                # 光标确实还在菜单上 → 什么都不做
    self._hover_menu.hide_with_anim()
    self._flush_deferred_leave()

def _flush_deferred_leave(self):
    if not self._hover_leave_deferred:
        return
    self._hover_leave_deferred = False
    if not self._hovering:
        self.character.handle_mouse_leave()
```

HoverMenu 的信号接线：

```python
self._hover_menu.menu_entered.connect(self._hover_grace_timer.stop)
self._hover_menu.menu_left.connect(
    lambda: self._hover_grace_timer.start(self._hover_grace_ms()))
```

**这一处是"鼠标能不能点得到菜单"的生死线**：
- 鼠标从人物 → 菜单：`leaveEvent` → 宽限期开始 → 进入菜单 → `menu_entered` → 取消宽限 → 菜单活着
- 鼠标从菜单 → 人物：`menu_left` → 宽限期开始 → `enterEvent` 取消 → 都活着
- 鼠标移开两者：宽限期到期 → 收菜单 + `handle_mouse_leave()` → 回 IDLE

**三个容易写错的细节**（实现时踩到过）：

1. **`_hover_leave_deferred` 必须在 `enterEvent` 里清掉**。只在宽限期到期时清会让标记一直陈旧：
   鼠标回到人物 → 之后再离开（此时菜单已被点击关闭，走 `else` 分支直接调了
   `handle_mouse_leave()`）→ 之后某次宽限期到期又补发一次，**leave 被发了两次**。
2. **`under_mouse()` 读的是真实全局光标位置**，所以依赖它的断言在自动化测试里会随
   "运行测试的人鼠标停在哪"随机成败。测试里必须把它替换成可控桩，两个分支各测一次。
3. **`hide_with_anim()` 是异步的**（160/180ms `QPropertyAnimation`，动画结束才真正 `hide()`），
   所以"菜单收起了吗"这类断言不能用固定 `qWait` 去等 —— 实测约 20% 概率随机失败。
   测试要**轮询等条件成立**（`wait_until(predicate)`），而不是"等一段时间"。

三条约定（阶段 F 的教训，改这一节前务必读）：

1. **发放与播报解耦**：物品先到手，台词说不说得出来是另一回事。被 90 秒间隔或专注保护
   挡下只是"这次没说出口"，不该把食物一起吞掉 —— 所以兑换/彩蛋场景走 `_speak()`
   （进 `dialogue.GAP_EXEMPT_SCENES`，不受间隔约束），节日台词走 `say()`（主动台词）
   并挂到 `_pending_speech` 上下次心跳补说。
2. **记日期的 flag 只在真的说出来了之后才写**（阶段 E 的教训）：先记会让"被挡一次"
   变成"这一天永远不再提醒"。
3. **播放动画是尽力而为**：签到不因"她正忙"而拒绝，`try_play_action()` 失败就算了 ——
   奖励是用户的，动画只是表现。

**心跳顺序就是优先级**（`on_idle_tick()`，一次心跳最多说一句，否则会互相顶掉）：

```
跨天重置 + 今日进度回写 → 补说挂起的节日台词 → 节日彩蛋 → 首用彩蛋
  → 陪伴/打字兑换 → 整点彩蛋 → 时段问候 → 长时间无输入（长待机彩蛋 → idle_long_absent）
  → 空闲闲聊
```

**今日进度的记账口径**（陪伴分钟 / 按键数）：

- `InputMonitor.any_activity` 在鼠标移动时每秒能来上百次，所以
  `notify_activity()` 里**只做浮点加法**（相邻两次输入的时间差，单次截断
  `ACTIVITY_GAP_CAP_SEC = 5` 秒 —— 挂机 3 小时后的第一次鼠标移动也只算 5 秒），
  存档由每分钟的心跳回写，且**值没变就不写**。
- 按键数同理只加内存整数。代价：进程被强杀时最多丢一分钟进度。

**九个结果码之外，签到多了两个**（`try_send()` 不返回它们）：

| 结果码 | 含义 |
|--------|------|
| `already` | 签到：今天已经签过了 |
| `clock_back` | 签到：系统时间被往回调 → **不发放、不重置**，只提一句 |

**九个结果码**（`try_send()` 的返回值，每一个都有专门测试）：

| 结果码 | 含义 |
|--------|------|
| `ok` | 送出去了，动画在播 |
| `empty` | 库存 0（含 `take_item()` 返回 False 的并发分支） |
| `unknown` | 物品名不在 `items.json` 里 |
| `capped` | 好感度到今日上限（**动画与台词照旧**，只额外跟一句） |
| `gift_capped` | 今日送礼次数已满 |
| `locked` | 她正忙（启动序列 / 上一个动画没播完） |
| `cooldown` | 连点防护 |
| `no_anim` | 素材全缺：只出台词，不播动画 |
| `disabled` | 养成关闭 / 当前角色不是 Q版 |

**三个必须记住的实现细节**

1. **`NurtureStore.__init__` 不读盘** —— `NurtureController.__init__` 里必须显式
   `self._store.load()`。漏掉的后果不是"数值从 0 开始"，而是**第一次 save 会把用户真档覆盖掉**。
   这个坑是写完 controller 才发现的，已加回归测试。
2. **`store` 里有一半是 `@property`**：`affection` / `affection_gained_today` /
   `gifts_sent_today` / `tease_count_today` / `streak` / `last_checkin_date` / `inventory`
   都是**属性**，写成 `store.affection()` 会 `TypeError: 'int' object is not callable`；
   而 `item_count()` / `take_item()` / `today()` / `mute_tease_today()` 才是方法。
3. **计数键必须用 `TODAY_KEYS` 里的名字**：`bump_today("gifts_sent")` 会直接抛
   `KeyError: 未知的每日计数器`，正确的是 `"gifts_sent_today"`。

**一处刻意偏差**：连点防护按"**送出瞬间** +300ms"实现，而 01 文档 6.3 写的是
"动画结束 +300ms"。原因是动画结束的时刻目前没有信号可听
（`CharacterController.interaction_finished` 声明了但从未 emit）。
300ms 的时长与目的完全一样，只是起点提前；动画播放期间面板本来就是收起的，
用户碰不到这个差异。阶段 E 接气泡时若需要"动画结束"这个时刻，再补 emit 也不迟。

## 5. 数据流

### 5.1 喂食（用户直接触发）

```
鼠标停留人物 600ms
  → PetWindow._show_hover_menu()          [检查 _hover_menu_allowed → character.is_busy()]
  → HoverMenu.popup_near(pet_geometry)    （贴人物下方）
  → 菜单弹出后调 character.handle_hover_menu_shown()（停掉长悬停问号）
  → 点击「喂食」→ action_triggered("feed")
  → PetWindow._on_hover_menu_action()
       ├ controller.on_menu_action("feed", pet_geometry) → True
       ├ hide_all_popups(except_key="nurture")   ← 菜单/功能面板/系统面板一起让位
       └ controller.show_panel(geo, "food")
            ├ store.reset_daily_if_needed()（跨天）
            ├ panel.set_inventory/affection/streak/today(...)  ← 从 store 灌数据
            └ panel.popup_near(geo)                        （贴人物左侧）
  → 点击食物卡片 → panel.item_chosen(name)
  → controller.on_item_chosen(name)
       ├ enabled()? → 不是 Q版/总开关关 → disabled
       ├ item(name)? → 不在 items.json → unknown
       ├ character.is_busy()? → locked
       ├ 冷却中? → cooldown
       ├ stock <= 0 → 说 feed_empty，**面板留着**
       ├ 礼物且今日已满 → 说 feed_empty，面板留着
       ├ store.take_item()  失败 → empty（并发抢库存）
       ├ model.apply_affection(...) → (新值, 实际增量) → store.set_affection(...)
       ├ model.resolve_anim(item, kind, registry_has) → action（四级兜底链）
       ├ character.play_action(action, lock=True) → 抛异常也吞掉
       ├ 选句 → speech_requested(text, tone) → （阶段 D：只写 debug_img.log）
       ├ state_changed.emit()
       └ 送出去了才 panel.hide_with_anim()
  → 动画播完 → GifCharacter._on_movie_finished() 的 INTERACTING 分支解锁 → 回 IDLE
```

### 5.2 主动台词（系统触发）

```
多个感知源 ──┐
  InputMonitor.any_activity ─→ NurtureController.on_activity()
  WindowMonitor.app_changed ─→ on_app_changed(key)
  WindowMonitor.fullscreen_changed ─→ on_fullscreen_changed(bool)
  AudioMonitor.*            ─→ on_audio(...)
  每分钟 tick               ─→ on_day_tick() / on_idle_tick()
                             │
                             ↓
                   can_speak(scene, tone)  ←── 冷却 / 全屏静默 / 最小间隔 / 专注与免打扰 / 禁区
                             │ 通过
                             ↓
                   dialogue.pick_line(scene, ctx)
                             │
                             ↓
                   bubble_should_say → SpeechBubble
```

**所有主动路径都必须过 `_can_speak`**，没有旁路。

### 5.3 获取途径（阶段 F，系统触发）

```
QTimer(60s).timeout ─→ NurtureController.on_idle_tick()
    │
    ├ 1. store.reset_daily_if_needed(today)  跨天 → 同步清零内存进度
    │     _sync_daily_progress()             今日进度回写存档（值没变就不写）
    ├ 2. flush_pending_speech()              上次被间隔挡下的节日台词，补说
    ├ 3. _check_event_egg(today)             events.json 命中 → 发物品 + 专属台词
    ├ 4. _check_first_run_egg()              一辈子一次：珍贵食物 ×1
    ├ 5. _check_conversions()                陪伴（60 分钟/个，上限 3）
    │                                        打字（2000 键/个，上限 2）
    │        └ 两个都走 model.convert_to_items(进度, 每份, 上限, 已兑)
    ├ 6. _check_hourly_egg(now)              每小时掷一次 25%，日上限 3
    ├ 7. 时段问候 → 长时间无输入（长待机彩蛋 → idle_long_absent）→ 空闲闲聊
    │
    └ 每一步：_grant_items() 是真发放 → try_play_action(点头/庆祝) 尽力而为
              → _speak()/_pending_speech 真说出来 → state_changed.emit()
```

**签走的是另一条路**（用户点了立刻结算，不等心跳）：

```
悬停菜单「签到」/ 托盘「今日签到」
  → NurtureController.try_checkin()
       ├ checkin_status(last, today) → same_day → already（说 checkin_already）
       │                              clock_back → 不发放不重置（说 checkin_clock_back）
       ├ next_streak() → 连签天数（含断签重置）
       ├ checkin_reward() → resolve_tiers() → 真物品名
       ├ store.set_checkin(streak, today)   ← **先记账**：库存满也要算签过
       ├ _grant_items() → 播 checkin_anim → 说一句
       │     优先级：inventory_full > checkin_milestone > checkin_done（**只出一句**）
       └ _grant_affection_value(reward.affection)
```

**菜单弹出的那一刻还会顺口提醒一次**（01 文档 4.1 第 2 条）：
`PetWindow._show_hover_menu()` → `controller.on_menu_shown()` → 今天没签且今天还没提醒过
→ 说 `checkin_remind` 并把 `checkin_reminded_date` 记成今天（**说出去了才记**）。

## 6. 性能

| 项 | 预期 | 保证方式 |
|----|------|----------|
| 前台窗口轮询 | 可忽略 | 1000ms 一次，四个 Win32 调用（`GetForegroundWindow` / `GetWindowThreadProcessId` / `OpenProcess`+`QueryFullProcessImageNameW` / DWM 取矩形），无内存分配峰值。`QueryFullProcessImageNameW` 读的是内核里的映像路径、**不会**去读目标进程的内存，所以目标进程卡死也不拖住我们；默认关闭时（`allow_foreground_detection: false`）**这个定时器根本不存在** |
| 输入计数 | 可忽略 | 回调里只做整数自增与 `deque.append`；主线程 1s 拉取一次 |
| 悬停菜单弹出 | 无卡顿 | 首帧预渲染到 `QPixmap` 缓存，之后复用 |
| 对话气泡 | 无卡顿 | 每次 `show_text` 重新排版（文字变了），但圆角路径缓存 |
| 常驻内存 | +< 1MB | 矢量图标缓存 + 无新增位图素材 |
| 存盘 | 无感 | 2s 防抖；单文件 < 5KB，`os.replace` 原子写 |

## 7. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 悬停菜单点不到（焦点/宽限期处理错） | 功能不可用 | 4.8(a) 的宽限期 + `menu_entered` 取消；**阶段 C 必须先单独验证"鼠标能从人物移到菜单并点到"再往下做** |
| 对话气泡抢焦点，打断用户打字 | 严重体验事故 | `WindowDoesNotAcceptFocus` + `WindowTransparentForInput` + `WA_ShowWithoutActivating`；阶段 E 用"边打字边触发气泡"专门验证 |
| 动到 `pet_window.py` 造成 PNG 回归 | 破坏红线 | 所有改动走新增分支 + 提前 return；阶段每步都跑 PNG 回归清单 |
| `handle_mouse_leave` 抑制导致角色卡在害羞态 | 状态机泄漏 | 宽限期到期**必定**调用一次 `handle_mouse_leave()`；用一个 `_hover_leave_deferred` 标志确保只延迟不丢失 |
| GIF 内建 loop=0 导致 `finished` 不触发 | 喂食动画卡住不解锁 | 沿用现有 `_on_frame_changed` 的"帧号归零"判定；`play_action` 走同一条 `_play_once` 路径，天然复用。**阶段 D 已用真实 GIF 验过**（`TestRealGifPlayback`） |
| `_locked` 忘记解开 → 她永远卡在吃东西的动作上 | 功能全废 | 解锁只有两条路（动画播完 / `release_lock()`），`stop()` 也清锁；单测点名全部 11 个入口 + 连喂 10 次 |
| 面板懒创建被 `_popups()` 意外触发 | 每开一次菜单多一个隐藏窗口 | `panel_widget()` 与 `panel()` 分开；有单测盯着 |
| 新存档没有库存 → 菜单全是灰的 | 阶段 D 无法实机验证（获取途径在阶段 F） | 交接时已手工种一份初始库存；`data/nurture.json` 就是普通 JSON，删掉即重置 |
| 用户把 `assets/nurture/` 删了 | 功能崩 | 所有加载点都有代码内默认值；缺失=功能降级，不是崩溃 |
| 前台窗口 API 在管理员进程上失败 | 感知缺失 | `OpenProcess` 失败返回 `""` → **连着 3 拍**读不到才降级成 `unknown`，静默降级、不崩不问 |
| 打包后 `assets/` 只读 | 设置写不回 | 用户覆盖写 `config.json`，不写 `assets/`（见 4.12） |
| 系统时间被改 | 刷签到 | `next_streak` 检测"今天 < 上次签到日" → 不发放不重置（`nurture_model` 可单测） |
